# Tasks / Work Board Requirements

เอกสารนี้เป็นข้อกำหนดเบื้องต้นของหน้า `/tasks` สำหรับระบบงานแบบบอร์ด รวมถึงกติกาเจ้าของงาน สมาชิก คำเชิญ และรายการที่ต้องเพิ่ม/แก้ในฐานข้อมูล

สถานะเอกสาร: Draft สำหรับใช้คุยร่วมกันระหว่าง Frontend, Backend และ Database

## 1. ความเข้าใจของระบบ

เมื่อผู้ใช้กดสร้าง “งาน” ระบบจะสร้าง **ตัวงาน/พื้นที่เก็บบอร์ด** ก่อน งานหนึ่งงานสามารถมีหลายบอร์ดอยู่ภายในได้ งานจึงไม่ใช่บอร์ดโดยตรง

ในหน้าสร้างงานต้องมีปุ่ม **“เพิ่มบอร์ด”** ให้ผู้ใช้เพิ่มบอร์ดได้หลายบอร์ดตามต้องการในฟอร์มเดียว งานหนึ่งงานสามารถสร้างพร้อมบอร์ดจำนวน `0..N` ได้ ผู้สร้างงานเป็น **เจ้าของงาน** โดยอัตโนมัติ และผู้สร้างบอร์ดเป็น **เจ้าของบอร์ด** โดยอัตโนมัติ

เจ้าของงานมีสิทธิ์จัดการงานและบอร์ดภายในงาน เจ้าของบอร์ดมีสิทธิ์เต็มในบอร์ดของตนเอง และไม่ควรสามารถเชิญตัวเองเข้าบอร์ดหรือการ์ดของตัวเองได้ เพราะเป็นเจ้าของอยู่แล้ว

หน้า `/tasks` ต้องมีอย่างน้อย 2 แท็บ:

1. **งานที่เราสร้าง** — งานที่ผู้ใช้เป็นเจ้าของ (`tasks.owner_id = current_user.id`) พร้อมแสดงจำนวนบอร์ดภายในงาน
2. **งานที่เราเข้าร่วม** — งานที่มีอย่างน้อยหนึ่งบอร์ดหรือการ์ดที่ผู้ใช้ตอบรับคำเชิญแล้ว

คำเชิญที่ยังไม่ตอบรับต้องไม่ถือว่าเป็นสมาชิกและต้องไม่มีสิทธิ์แก้ไขข้อมูล คำเชิญควรแสดงผ่าน notification/inbox เพื่อให้ผู้ใช้กดตอบรับหรือปฏิเสธ

## 2. โครงสร้างข้อมูลที่ผู้ใช้เห็น

```text
งาน (Work / Task container)
└── บอร์ดงาน (Board)
    └── คอลัมน์/หมวดภายในบอร์ด (List — โครงสร้างภายใน ไม่ใช่ระดับสิทธิ์)
        └── การ์ดงาน (Card)
            └── รายการย่อย (Sub-item / Checklist)
```

คำเรียกในเอกสารนี้:

| คำที่ผู้ใช้เห็น | ตารางหลักปัจจุบัน | ความหมาย |
|---|---|---|
| งาน | `tasks` | ตัวเก็บบอร์ดทั้งหมดของงานนั้น |
| บอร์ดงาน | `task_boards` (ตารางใหม่) | พื้นที่ทำงานหนึ่งบอร์ดภายในงาน |
| คอลัมน์/หมวด | `task_lists` | กลุ่มสำหรับจัดวางการ์ด เช่น To do, Doing, Done |
| การ์ดงาน | `task_cards` | งานที่ต้องทำจริงภายในบอร์ด |
| รายการย่อย | `task_sub_items` | Checklist หรือขั้นตอนย่อยของการ์ด |

`task_lists` มีอยู่ใน schema ปัจจุบันและหน้า UI ใช้สำหรับจัดกลุ่มการ์ด จึงยังคงไว้ได้ แต่ไม่ควรนำไปแสดงเป็น “ชนิดงาน” เพิ่มเติมจนผู้ใช้เข้าใจว่ามี 5 ระดับ

## 3. กติกาการสร้างงาน

### 3.1 เมื่อสร้างงานและบอร์ดจากหน้าเดียวกัน

- สร้างแถวใหม่ใน `tasks`
- บันทึกผู้สร้างลงใน `tasks.owner_id` ในฐานะเจ้าของงาน
- หน้า form ต้องมีปุ่ม “เพิ่มบอร์ด” เพื่อเพิ่มข้อมูลบอร์ดหลายรายการ เช่น ชื่อบอร์ดและรายละเอียด
- ผู้ใช้เลือกได้ว่าจะสร้างงานเปล่า หรือสร้างงานพร้อมบอร์ดจำนวนกี่บอร์ดก็ได้
- ถ้ามีบอร์ดใน form ให้สร้างแถวใน `task_boards` โดยผูกกับงานใหม่ผ่าน `work_id`
- บอร์ดที่สร้างพร้อมงานให้ `task_boards.owner_id = current_user.id`
- ไม่สร้าง `task_cards` หรือ `task_sub_items` อัตโนมัติจากการสร้างงาน/บอร์ด
- ไม่แปลงชื่อ/รายละเอียดของงานไปเป็นรายการย่อย
- การสร้างงานและบอร์ดทั้งหมดต้องทำใน transaction เดียวกัน เพื่อไม่ให้เกิดงานที่สร้างไม่ครบหรือบอร์ดหลุดจากงาน
- หลังสร้างสำเร็จ ผู้ใช้ยังสามารถกด “เพิ่มบอร์ด” จากหน้ารายละเอียดงานเพื่อสร้างบอร์ดเพิ่มภายหลังได้

### 3.2 เมื่อสร้างบอร์ดงาน

- ผู้ใช้กด “สร้างบอร์ด” จากภายในงานที่ตนเองมีสิทธิ์
- สร้างแถวใหม่ใน `task_boards` และผูกด้วย `task_boards.work_id = tasks.id`
- บันทึกผู้สร้างลงใน `task_boards.owner_id`
- ไม่สร้าง `task_cards` หรือ `task_sub_items` อัตโนมัติ
- หาก UI ของบอร์ดต้องมีคอลัมน์เริ่มต้น ให้สร้าง `task_lists` ค่าเริ่มต้นได้ แต่ต้องไม่สร้างการ์ดหรือรายการย่อย
- ผู้สร้างบอร์ดมีสถานะเจ้าของทันที ไม่ต้องเชิญและไม่ต้องตอบรับคำเชิญ
- การสร้างบอร์ดและข้อมูลเริ่มต้นต้องทำใน transaction เดียวกัน

### 3.3 การสร้างการ์ดงาน

- ผู้ที่มีสิทธิ์ระดับบอร์ด หรือเจ้าของบอร์ด สามารถสร้าง `task_cards`
- การ์ดต้องอยู่ใน `task_lists` ที่เป็นของบอร์ดเดียวกัน
- การ์ดใหม่ไม่จำเป็นต้องมีรายการย่อย
- รายการย่อยจะถูกสร้างภายหลังจากหน้า detail ของการ์ดเท่านั้น

### 3.4 การสร้างรายการย่อย

- สร้างจากการ์ดที่มีอยู่แล้วเท่านั้น
- ต้องตรวจสอบว่า `card_id` อยู่ในบอร์ดเดียวกับรายการย่อยที่กำลังสร้าง
- ห้ามใช้ endpoint สร้างงานหรือสร้างบอร์ดเพื่อสร้างรายการย่อยแฝง

## 4. ระบบคำเชิญและสิทธิ์

มีคำเชิญ 2 ขอบเขต แยกกันชัดเจน:

### 4.1 เชิญเข้าบอร์ดงาน

การเชิญเข้าบอร์ดของบอร์ดใดบอร์ดหนึ่งจะส่งคำเชิญไปยังผู้ใช้เป้าหมาย เมื่อผู้ใช้กด **ตอบรับ** จึงสร้างสมาชิกในบอร์ดและเริ่มแก้ไขบอร์ดนั้นได้ การเชิญเข้าบอร์ดไม่ควรทำให้ผู้ใช้เป็นเจ้าของงานโดยอัตโนมัติ

สิทธิ์หลังตอบรับคำเชิญเข้าบอร์ด:

- ดูบอร์ดและข้อมูลภายในบอร์ด
- แก้ไขข้อมูลบอร์ดตาม role ที่ได้รับ
- เพิ่ม/แก้ไขการ์ดและรายการย่อยตามสิทธิ์ของบอร์ด
- ไม่มีสิทธิ์จัดการเจ้าของบอร์ด
- การจัดการคำเชิญควรสงวนไว้ให้เจ้าของบอร์ดก่อน เว้นแต่จะกำหนด role ผู้จัดการภายหลัง

สถานะคำเชิญที่ต้องรองรับ: `pending`, `accepted`, `rejected`, `cancelled`, `expired`

### 4.2 เชิญเข้าการ์ดงาน

การเชิญเข้าการ์ดจะให้สิทธิ์เฉพาะการ์ดนั้น ไม่เท่ากับการเป็นสมาชิกที่แก้ไขได้ทั้งบอร์ด

สิทธิ์หลังตอบรับคำเชิญเข้าการ์ด:

- ดูบอร์ดได้เท่าที่จำเป็นเพื่อเข้าถึงการ์ดที่ได้รับเชิญ
- แก้ไขการ์ดที่ได้รับเชิญ
- เพิ่ม/แก้ไข/ทำรายการย่อยของการ์ดนั้น
- ไม่สามารถแก้ไขการ์ดอื่นหรือ metadata ของบอร์ด เว้นแต่มีสิทธิ์จากคำเชิญเข้าบอร์ดด้วย

หมายเหตุ: หากผู้ใช้เป็นสมาชิกบอร์ดอยู่แล้ว การเชิญเข้าการ์ดเป็นการเพิ่ม scope เฉพาะการ์ด ไม่ต้องสร้างสมาชิกบอร์ดซ้ำ

### 4.3 กฎป้องกันการเชิญตัวเอง

ต้องบังคับทั้ง Backend และ Database guard/trigger:

- `invited_user_id` ต้องไม่เท่ากับผู้ใช้ที่กำลังเชิญ
- เจ้าของบอร์ดไม่สามารถถูกเชิญเข้าบอร์ดของตัวเอง
- เจ้าของบอร์ดไม่สามารถถูกเชิญเข้าการ์ดในบอร์ดของตัวเอง
- ห้ามมีคำเชิญ `pending` ซ้ำสำหรับ scope และผู้ใช้คนเดียวกัน
- ต้องตรวจสอบว่าผู้ใช้เป้าหมายมีอยู่จริงและมีสถานะ `active`
- การซ่อนปุ่มเชิญตัวเองใน UI เป็นเพียง UX ส่วนการตรวจสอบจริงต้องอยู่ที่ API

## 5. สิทธิ์ที่ต้องตรวจสอบทุกครั้ง

ห้ามใช้เพียงการซ่อน/แสดงปุ่มบน Frontend เพื่อควบคุมสิทธิ์ ทุก mutation ต้องตรวจสอบผู้ใช้ปัจจุบันที่ Backend และควรมี RLS/policy หากใช้ Supabase โดยตรง

| การกระทำ | เจ้าของบอร์ด | สมาชิกบอร์ดที่ตอบรับ | สมาชิกการ์ดที่ตอบรับ | คำเชิญ pending |
|---|---:|---:|---:|---:|
| ดูบอร์ด | ได้ | ได้ | ได้เท่าที่จำเป็น | ไม่ได้ |
| แก้ไขข้อมูลบอร์ด | ได้ | ได้ตาม role | ไม่ได้ | ไม่ได้ |
| สร้างการ์ด | ได้ | ได้ | ไม่ได้ | ไม่ได้ |
| แก้ไขการ์ด | ได้ | ได้ | ได้เฉพาะการ์ดที่รับ | ไม่ได้ |
| แก้ไขรายการย่อย | ได้ | ได้ | ได้เฉพาะการ์ดที่รับ | ไม่ได้ |
| เชิญสมาชิกบอร์ด | ได้ | ไม่ได้ในรุ่นแรก | ไม่ได้ | ไม่ได้ |
| ลบบอร์ด | ได้ | ไม่ได้ | ไม่ได้ | ไม่ได้ |

## 6. พฤติกรรมของแท็บหน้า `/tasks`

### งานที่เราสร้าง

ใช้งานที่ผู้ใช้ปัจจุบันเป็นเจ้าของเท่านั้น:

```text
tasks.owner_id = current_user.id
```

หน้า list ควรแสดงจำนวนบอร์ดในแต่ละงาน และให้กดเข้าไปดู/สร้างบอร์ดภายในงานได้ ไม่ควรเปิดเป็นบอร์ดทันทีตั้งแต่การ์ดงานระดับบนสุด

ไม่ควรใช้ `assigned_by` เป็นตัวแทนเจ้าของในระยะยาว เพราะ `assigned_by` มีความหมายว่าใครมอบหมายงานเดิม ไม่ใช่ owner ของงาน

### งานที่เราเข้าร่วม

แสดงงานที่มีข้อมูลที่เข้าเงื่อนไขอย่างใดอย่างหนึ่ง:

- มีแถวใน `task_board_members` ของบอร์ดใดบอร์ดหนึ่งในงาน
- มีแถวใน `task_card_members` ของการ์ดใดการ์ดหนึ่งในงาน

ไม่รวมรายการที่มีเพียงคำเชิญ `pending`, `rejected`, `cancelled` หรือ `expired`

ควรแสดง badge แยกให้ผู้ใช้รู้ว่าเข้าร่วมแบบใด:

- `Board member` — แก้ไขได้ตามสิทธิ์ระดับบอร์ด
- `Card member` — แก้ไขได้เฉพาะการ์ดที่ได้รับสิทธิ์

## 7. รายการ Database ที่ต้องเพิ่ม/แก้

### 7.1 แก้ตาราง `tasks`

| รายการ | การเปลี่ยนแปลง |
|---|---|
| `owner_id` | เพิ่ม `uuid NOT NULL` และ Foreign Key ไป `users(id)` |
| `record_kind` | กำหนดค่าใหม่สำหรับงานที่สร้างตาม flow นี้ เช่น `work`; ของเดิมให้ถือเป็น legacy จนกว่าจะ migrate |
| `assigned_by` | คงไว้เพื่อรองรับข้อมูลเดิม/ประวัติการมอบหมาย ไม่ใช้แทน owner ใหม่ |
| `assigned_to` | คงไว้ชั่วคราวเพื่อ compatibility กับระบบเดิม ไม่ใช้เป็นสมาชิกบอร์ดหลัก |

การ backfill เบื้องต้น: ใช้ `assigned_by` เป็น `owner_id` สำหรับข้อมูลเก่าที่มีค่า หากไม่มีค่าให้ระบุผู้ดูแลเพื่อกำหนด owner อย่างชัดเจนก่อนบังคับ `NOT NULL`

### 7.2 เพิ่มตาราง `task_boards`

ใช้เก็บบอร์ดทั้งหมดที่อยู่ภายในงานหนึ่งงาน

คอลัมน์ที่ต้องมี:

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `work_id uuid NOT NULL` → `tasks(id)`
- `name text NOT NULL`
- `description text NOT NULL DEFAULT ''`
- `owner_id uuid NOT NULL` → `users(id)`
- `status text NOT NULL DEFAULT 'active'`
- `sort_order integer NOT NULL DEFAULT 0`
- `created_at timestamptz NOT NULL DEFAULT now()`
- `updated_at timestamptz NOT NULL DEFAULT now()`

ควรมี index ที่ `task_boards(work_id)` และ `task_boards(owner_id)`

### 7.3 เพิ่มตาราง `task_board_members`

ใช้เก็บสมาชิกที่ตอบรับแล้วหรือสมาชิกที่ระบบสร้างให้อัตโนมัติในฐานะ owner

คอลัมน์ที่ต้องมี:

- `board_id uuid NOT NULL` → `task_boards(id)`
- `user_id uuid NOT NULL` → `users(id)`
- `role text NOT NULL DEFAULT 'editor'` เช่น `owner`, `editor`
- `joined_at timestamptz NOT NULL DEFAULT now()`
- `created_at timestamptz NOT NULL DEFAULT now()`
- Primary Key หรือ Unique Key: `(board_id, user_id)`

### 7.4 เพิ่มตาราง `task_board_invitations`

ใช้เป็น source of truth ของคำเชิญเข้าบอร์ด ไม่ใช้ `notifications` แทน เพราะ notification เป็นเพียงช่องทางแจ้งเตือน

คอลัมน์ที่ต้องมี:

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `board_id uuid NOT NULL` → `task_boards(id)`
- `invited_user_id uuid NOT NULL` → `users(id)`
- `invited_by uuid NOT NULL` → `users(id)`
- `role text NOT NULL DEFAULT 'editor'`
- `status text NOT NULL DEFAULT 'pending'` พร้อม check: `pending`, `accepted`, `rejected`, `cancelled`, `expired`
- `message text NOT NULL DEFAULT ''`
- `responded_at timestamptz`
- `expires_at timestamptz`
- `created_at timestamptz NOT NULL DEFAULT now()`

ควรมี unique/partial index ป้องกันคำเชิญ pending ซ้ำต่อ `(board_id, invited_user_id)`

### 7.5 เพิ่มตาราง `task_card_members`

ใช้เก็บสิทธิ์การ์ดที่ตอบรับแล้ว

คอลัมน์ที่ต้องมี:

- `card_id uuid NOT NULL` → `task_cards(id)`
- `user_id uuid NOT NULL` → `users(id)`
- `role text NOT NULL DEFAULT 'editor'`
- `joined_at timestamptz NOT NULL DEFAULT now()`
- `created_at timestamptz NOT NULL DEFAULT now()`
- Primary Key หรือ Unique Key: `(card_id, user_id)`

### 7.6 เพิ่มตาราง `task_card_invitations`

โครงสร้างเหมือน `task_board_invitations` แต่ใช้ `card_id` เป็น scope:

- `id uuid PRIMARY KEY DEFAULT gen_random_uuid()`
- `card_id uuid NOT NULL` → `task_cards(id)`
- `invited_user_id uuid NOT NULL` → `users(id)`
- `invited_by uuid NOT NULL` → `users(id)`
- `role text NOT NULL DEFAULT 'editor'`
- `status text NOT NULL DEFAULT 'pending'`
- `message text NOT NULL DEFAULT ''`
- `responded_at timestamptz`
- `expires_at timestamptz`
- `created_at timestamptz NOT NULL DEFAULT now()`

ควรมี unique/partial index ป้องกันคำเชิญ pending ซ้ำต่อ `(card_id, invited_user_id)`

### 7.7 แก้ความสัมพันธ์ตารางเดิม

ตารางปัจจุบันยังผูก `task_lists.task_id` ไปที่ `tasks` โดยตรง แต่ตาม requirement ใหม่ `task_lists` ต้องอยู่ใต้บอร์ด:

- เพิ่ม `task_lists.board_id uuid` → `task_boards(id)`
- Backfill `board_id` ให้ข้อมูลเดิมด้วย mapping ที่ทีม Backend/Database ยืนยัน
- หลังตรวจสอบแล้ว ให้เลิกใช้หรือเปลี่ยนชื่อ `task_lists.task_id` ที่เคยชี้ `tasks(id)`
- ทุก `task_cards` ต้องตรวจ parent board ผ่าน `task_cards.list_id → task_lists.board_id`
- `task_sub_items` ต้องยึด `card_id` เป็น parent หลัก ไม่ใช้ `task_id` เป็นตัวบอกบอร์ด/งานอีกต่อไป
- สำหรับข้อมูลเก่า ให้คงคอลัมน์เดิมไว้ชั่วคราวจน migration เสร็จและทดสอบครบ

### 7.8 ใช้ตารางเดิมที่เกี่ยวข้อง

- `users`: ตรวจสอบผู้ใช้เป้าหมายและสถานะ `active`
- `task_lists`: คอลัมน์/หมวดของบอร์ด ไม่ใช่ระดับงานและไม่ใช่ invitation scope
- `task_cards`: การ์ดงาน
- `task_sub_items`: รายการย่อยของการ์ด
- `notifications`: แจ้งเตือนคำเชิญและผลการตอบรับ โดยเก็บ invitation id ใน `metadata`
- `task_events`: บันทึก audit เช่น `board_created`, `board_invited`, `board_invitation_accepted`, `card_invited`, `card_invitation_accepted`
- `task_assignees`, `card_assignees`, `list_assignees`: ใช้สำหรับ assignment ของงาน ไม่ควรใช้แทน membership/invitation

## 8. Flow ที่ต้องรองรับ

### สร้างงานพร้อมบอร์ดหลายบอร์ด

```text
ผู้ใช้เปิดหน้าสร้างงาน
  → กรอกข้อมูลงาน
  → กด “เพิ่มบอร์ด” ได้ 0..N ครั้ง
  → กรอกชื่อ/รายละเอียดของแต่ละบอร์ด
  → POST สร้าง tasks.owner_id = current_user.id
  → สร้าง task_boards ทุกบอร์ดที่อยู่ใน form โดยผูก work_id กับ tasks.id
  → ไม่สร้าง task_cards/task_sub_items
  → สร้าง task_events: work_created
  → แสดง event board_created สำหรับแต่ละบอร์ดที่สร้าง
  → แสดงงานพร้อมรายการบอร์ดใน “งานที่เราสร้าง”
```

### สร้างบอร์ดในงาน

```text
ผู้ใช้เปิดงานและกด “สร้างบอร์ด”
  → ตรวจสิทธิ์เจ้าของงานหรือสิทธิ์ที่กำหนด
  → POST สร้าง task_boards.work_id = task.id
  → บันทึก task_boards.owner_id = current_user.id
  → สร้าง task_lists ค่าเริ่มต้นได้ถ้าหน้าบอร์ดต้องใช้
  → ไม่สร้าง task_cards/task_sub_items
  → สร้าง task_events: board_created
  → แสดงบอร์ดภายในงานนั้น
```

### เชิญเข้าบอร์ด

```text
เจ้าของเลือกผู้ใช้
  → ตรวจว่าไม่ใช่ตัวเองและไม่มี pending ซ้ำ
  → สร้าง task_board_invitations(board_id, status = pending)
  → สร้าง notifications
  → ผู้รับกดตอบรับ
  → เปลี่ยน invitation เป็น accepted
  → สร้าง task_board_members
  → บันทึก task_events
```

การเปลี่ยนสถานะ invitation และการสร้าง member ต้องอยู่ใน transaction เดียวกัน และต้องทำซ้ำอย่างปลอดภัยได้ (idempotent)

### เชิญเข้าการ์ด

```text
ผู้มีสิทธิ์เลือกการ์ดและผู้ใช้
  → ตรวจว่าไม่ใช่ตัวเองและไม่มี pending ซ้ำ
  → สร้าง task_card_invitations(status = pending)
  → สร้าง notifications
  → ผู้รับกดตอบรับ
  → เปลี่ยน invitation เป็น accepted
  → สร้าง task_card_members
  → บันทึก task_events
```

## 9. API ที่ควรมี

ชื่อ endpoint ปรับตามมาตรฐาน Backend ที่ใช้อยู่ได้ แต่ต้องมีความสามารถเทียบเท่านี้:

| ความสามารถ | Endpoint ที่แนะนำ |
|---|---|
| ดึงบอร์ดที่สร้าง/เข้าร่วม | `GET /api/tasks?scope=owned` และ `GET /api/tasks?scope=joined` |
| สร้างงาน | `POST /api/tasks` |
| สร้างงานพร้อมบอร์ด | `POST /api/tasks` โดยรับ `boards: []` หรือ `boards: [{ name, description }]` |
| ดึงบอร์ดในงาน | `GET /api/tasks/:taskId/boards` |
| สร้างบอร์ดในงาน | `POST /api/tasks/:taskId/boards` |
| เชิญเข้าบอร์ด | `POST /api/task-boards/:boardId/invitations` |
| เชิญเข้าการ์ด | `POST /api/tasks/cards/:cardId/invitations` |
| ดูคำเชิญของฉัน | `GET /api/task-invitations/me` |
| ตอบรับ/ปฏิเสธคำเชิญ | `POST /api/task-invitations/:invitationId/respond` |
| ยกเลิกคำเชิญ | `POST /api/task-invitations/:invitationId/cancel` |

คำตอบรับควรรับเฉพาะ `accepted` หรือ `rejected` และต้องตรวจว่า invitation เป็นของผู้ใช้ปัจจุบัน ห้ามให้ client ส่ง `invited_user_id` ใหม่ตอนตอบรับ

## 11. Acceptance Criteria

- ผู้ใช้สร้างงานแล้วเห็นงานในแท็บ “งานที่เราสร้าง”
- หน้า “สร้างงาน” มีปุ่ม “เพิ่มบอร์ด” และเพิ่มบอร์ดได้หลายรายการ
- ผู้ใช้สร้างงานเปล่าได้เมื่อไม่ได้เพิ่มบอร์ด
- ผู้ใช้สร้างงานพร้อมบอร์ดจำนวนหลายบอร์ดได้ในครั้งเดียว
- บอร์ดที่สร้างใหม่ไม่มีการ์ดหรือรายการย่อยที่ระบบสร้างให้เอง
- ผู้สร้างเป็น owner โดยอัตโนมัติและไม่มีปุ่มเชิญตัวเอง
- ผู้ใช้ที่ถูกเชิญยังแก้ไขไม่ได้จนกว่าจะตอบรับ
- การตอบรับคำเชิญเข้าบอร์ดสร้าง board membership และแก้ไขบอร์ดได้ตาม role
- การตอบรับคำเชิญเข้าการ์ดแก้ไขได้เฉพาะการ์ดนั้นและรายการย่อยของการ์ดนั้น
- คำเชิญซ้ำใน scope เดียวกันถูกป้องกัน
- API ป้องกันการปลอม `user_id`, `task_id`, `card_id` และป้องกันการข้ามบอร์ด
- แท็บ “งานที่เราเข้าร่วม” ไม่แสดงคำเชิญที่ยัง pending เป็นสมาชิก
- ทุกการเชิญและการตอบรับมี notification และ audit event

## 13. ข้อสังเกตจาก Schema ปัจจุบัน

- `tasks` มี `assigned_by` และ `assigned_to` แต่ยังไม่มี `owner_id` จึงยังแยก “เจ้าของงาน” กับ “ผู้รับมอบหมาย” ไม่ได้อย่างถูกต้อง
- Schema ปัจจุบันยังไม่มีตารางบอร์ดแยก ทำให้ต้องเพิ่ม `task_boards` เพื่อให้หนึ่งงานเก็บได้หลายบอร์ด
- มี `task_assignees` แล้ว แต่ตารางนี้เหมาะกับการมอบหมายงาน ไม่ใช่สมาชิกที่ตอบรับคำเชิญ
- มี `notifications` แล้ว แต่ไม่ควรใช้เป็นตารางคำเชิญ เพราะไม่มีสถานะตอบรับและไม่เหมาะกับการบังคับสิทธิ์
- `task_cards` เชื่อมกับบอร์ดผ่าน `task_lists.board_id`; ทุก API ที่รับ `card_id` ต้องตรวจ parent board และ parent work จากความสัมพันธ์นี้ก่อนอนุญาต
- Schema snapshot มีตารางที่เกี่ยวข้องกับ `projects` และ `project_members` อยู่ด้วย เอกสารนี้ใช้โมเดล `tasks` เป็นบอร์ดตามหน้า `/tasks` ปัจจุบัน และยังไม่รวมการย้ายไปใช้ `projects` จนกว่าจะมีการตัดสินใจแยก scope

## 14. แนวทาง UI/UX ของหน้า `/tasks`

### Design direction

ต้องการหน้าตาแบบ **Clean, Simple, Calm และใช้งานง่าย** ให้ข้อมูลและลำดับงานเด่นกว่าการตกแต่ง โดยหลีกเลี่ยงการทำ UI ที่เข้ม หนา หรือมีองค์ประกอบแย่งความสนใจมากเกินไป

### หลักการออกแบบ

- ใช้พื้นหลังสีอ่อนหรือขาวเป็นหลัก
- ใช้สีเทาอ่อนสำหรับเส้นแบ่งและพื้นผิวรอง
- ใช้สีหลักเฉพาะจุดที่ต้องการสื่อสถานะหรือ action สำคัญ
- หลีกเลี่ยงพื้นหลังสีทึบเข้มขนาดใหญ่, gradient จัด, glow, glass effect และเงาหนัก
- ใช้ border บาง ๆ และ shadow เบามากเท่าที่จำเป็น
- ใช้พื้นที่ว่างและระยะห่างเพื่อแบ่งกลุ่มข้อมูล แทนการใช้กล่องสีเข้มหลายชั้น
- ปุ่มควรเรียบ อ่านง่าย และไม่ใช้สีเด่นทุกปุ่ม
- ใช้ icon เท่าที่จำเป็น และต้องมี label เมื่อ action อาจตีความได้หลายแบบ
- Modal และ drawer ควรมีพื้นหลังขาว/อ่อน ไม่ทำ overlay ดำทึบเกินไป
- ลดจำนวน badge และสีสถานะที่แสดงพร้อมกัน เพื่อไม่ให้หน้าดูรก

### Modal / หน้าต่างสร้างงานและบอร์ด

Modal ของการสร้างงาน เพิ่มบอร์ด เชิญสมาชิก และยืนยันการกระทำ ควรแสดงอยู่ **กึ่งกลางหน้าจอทั้งแนวตั้งและแนวนอน** ไม่ติดอยู่ด้านบนของหน้า

- ใช้ `display: flex`, `align-items: center` และ `justify-content: center`
- พื้นหลัง overlay ใช้สีดำโปร่งบาง ๆ ประมาณ `rgba(15, 23, 42, 0.18)` ไม่ทึบจนหน้าด้านหลังมืดเกินไป
- กล่อง Modal ใช้พื้นหลังขาว ขอบบาง และเงาอ่อน
- ความกว้างแนะนำประมาณ `min(92vw, 560px)` สำหรับฟอร์มทั่วไป และ `min(94vw, 760px)` สำหรับฟอร์มที่มีรายการบอร์ดหลายรายการ
- มี header ชัดเจน: ชื่อ Modal ด้านซ้าย และปุ่มปิดด้านขวา
- เนื้อหาด้านในควรมีระยะห่างสม่ำเสมอ และแบ่งส่วนงาน/บอร์ดด้วยเส้นบางหรือพื้นที่ว่างแทนกล่องสีเข้ม
- ปุ่มหลักและปุ่มยกเลิกอยู่ด้านล่างของ Modal ในตำแหน่งที่สแกนหาได้ง่าย
- Modal ที่มีรายการบอร์ดหลายรายการควรให้ส่วนรายการเลื่อนได้เฉพาะด้านใน โดย header และปุ่ม action ยังมองเห็นได้
- บนมือถือให้ Modal กว้างเกือบเต็มจอ มีระยะขอบรอบกล่อง และไม่ให้เนื้อหาถูกตัดใต้ขอบจอ
- กด `Esc` เพื่อปิดได้เมื่อไม่มีข้อมูลที่ยังไม่ได้บันทึก; หากมีข้อมูลให้แสดง confirmation ก่อนปิด
- ไม่ควรใช้ Modal แบบเต็มหน้าจอหรือชิดขอบบน เว้นแต่เป็น flow ที่มีข้อมูลจำนวนมากจริง ๆ

```text
ชื่อหน้า + ปุ่มสร้างงาน
  → แท็บ งานที่เราสร้าง / งานที่เราเข้าร่วม
  → ค้นหาและ filter งานแบบเรียบ
  → รายการงาน พร้อมจำนวนบอร์ด
  → หน้า/Modal สร้างงานมีปุ่ม “เพิ่มบอร์ด” หลายครั้งได้
  → เปิดงานเพื่อดูบอร์ด หรือกด “เพิ่มบอร์ด” ภายหลัง
  → เปิดบอร์ดเพื่อดู List / Card / Sub-item
```

### พฤติกรรมที่ควรมี

- แท็บที่เลือกใช้เส้นหรือพื้นสีอ่อนเพื่อบอกสถานะ ไม่ใช้แถบสีเข้มขนาดใหญ่
- Empty state ควรใช้ข้อความสั้น ๆ และปุ่ม action เดียวที่ชัดเจน
- Loading ใช้ skeleton หรือ spinner ขนาดเล็ก ไม่ใช้หน้าจอ overlay ทึบทั้งหน้า
- Error แสดงเป็นข้อความสุภาพใกล้ส่วนที่ผิดพลาด พร้อมปุ่มลองใหม่
- การตอบรับคำเชิญใช้ confirmation ที่ชัดเจน แต่ไม่รบกวนการใช้งานเกินจำเป็น
- บนมือถือให้ card และ filter เรียงเป็นแนวตั้ง และไม่บังคับให้เลื่อนแนวนอนโดยไม่จำเป็น

### สิ่งที่ควรหลีกเลี่ยง

- Dashboard-style card ที่มีสีเข้มและเงาหนักจำนวนมาก
- Gradient หรือสีสดเต็มพื้นที่
- Modal ที่พื้นหลังดำทึบจนรู้สึกเหมือนเปลี่ยนหน้า
- ปุ่มหลายปุ่มที่ใช้สี primary พร้อมกันจนไม่รู้ว่าควรกดอะไร
- การซ่อนข้อมูลสำคัญไว้ใน icon อย่างเดียว
- การแสดงรายละเอียดทุกระดับพร้อมกันจนผู้ใช้แยก Board, Card และ Sub-item ไม่ออก
